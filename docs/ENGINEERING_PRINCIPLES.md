**Project:** Trading Operating System (TOS) Professional Edition

**Document Version:** 1.0

**Status:** Active

# Purpose

This document defines the engineering philosophy and development standards of the Trading Operating System (TOS).

Its purpose is to ensure that every feature, module and architectural decision is developed consistently throughout the lifetime of the project.

Whenever implementation decisions conflict with convenience, these principles take precedence.

---

# Vision

TOS is not intended to become another trading journal.

It is designed to become a complete Trading Operating System that assists with:

- Decision making
- Trade planning
- Risk management
- Trade execution
- Performance analysis
- Psychological development
- Continuous improvement

Every engineering decision should support this long-term vision.

---

# Core Engineering Philosophy

The project follows several fundamental principles.

## 1. Domain First

Business logic belongs inside the domain layer.

The user interface should display information.

It should not contain business rules.

The Trade Domain is the single source of truth.

---

## 2. Specification Before Implementation

Every significant feature begins with a written specification.

Implementation begins only after the specification has been reviewed and frozen.

Specifications are treated as contracts.

---

## 3. One Source of Truth

Every business rule exists in one location only.

Examples include:

- Process Score calculation
- Readiness Score calculation
- Position sizing rules
- Lifecycle transitions

Duplicating business rules is prohibited.

---

## 4. Computed Values

Computed values are never edited manually.

Examples include:

- Average Entry
- Average Exit
- Readiness Score
- Process Score
- R-Multiple
- Realised Profit and Loss

These values are generated by the Validation Engine.

---

## 5. Validation Before Transition

No trade may advance through its lifecycle unless validation succeeds.

Every lifecycle transition is verified before it is accepted.

---

## 6. Separation of Responsibilities

Each module should have one clear responsibility.

Examples:

Trade Planning

- why a trade exists

Trade Execution

- how the trade entered

Trade Management

- what changed during the trade

Trade Review

- evaluation after completion

Trade Learning

- improvements for future trades

---

## 7. Small Incremental Development

Large implementations are divided into small batches.

Each batch follows the same process:

Design

↓

Implement

↓

Compile

↓

Review

↓

Commit

↓

Push

No batch is considered complete until compilation succeeds.

---

## 8. Clean Build Rule

The project should always compile successfully.

Known compilation errors must never be committed intentionally.

---

## 9. Documentation Is Part Of The Product

Documentation is maintained alongside implementation.

Architecture documents are considered part of the codebase.

Major architectural decisions must always be documented.

---

## 10. Readability Over Cleverness

Readable code is preferred over clever code.

Future maintainability has priority over writing fewer lines.

Every module should be understandable without requiring advanced language knowledge.

---

# Domain Model Principles

The Trade Domain represents the business.

The domain should remain independent from:

- React
- UI components
- Browser APIs
- Storage technologies

The domain must remain portable.

---

# Validation Principles

Validation should answer:

Is this trade internally consistent?

Validation should never silently modify business data.

Instead it should:

- detect
- report
- explain

Every validation message should be actionable.

---

# Factory Principles

Trade creation is centralised.

Trade objects should never be assembled manually throughout the application.

Factories guarantee consistent initialisation.

---

# Storage Principles

Persistence should remain independent from business logic.

Changing storage technology should not require changes to the Trade Domain.

---

# User Interface Principles

The interface should assist decision making.

It should reduce cognitive load.

It should highlight important information rather than maximise visual complexity.

Every screen should answer:

"What decision should the trader make next?"

---

# Error Handling

Errors should be:

- descriptive
- traceable
- actionable

Generic errors should be avoided whenever practical.

---

# Future Compatibility

Every new feature should be evaluated against:

- maintainability
- scalability
- testability
- readability
- extensibility

Short-term convenience must never compromise long-term architecture.

---

# Definition of Done

A feature is complete only when:

- Specification is complete.
- Documentation is updated.
- Code compiles successfully.
- Validation passes.
- Architecture remains consistent.
- No duplicated business logic exists.
- Build log is updated.
- Changelog is updated.
- Code has been reviewed.

# Guiding Principle

The objective of TOS is not simply to record trades.

Its objective is to help the trader consistently make better trading decisions through disciplined processes, structured data and reliable software engineering.
# Development Workflow Standards

These standards apply to every implementation throughout the TOS Professional Edition project.

---

## 1. Terminal First Principle

Whenever a task can be completed safely from the terminal, the terminal is the preferred interface over the graphical file explorer.

Examples include:

- Creating folders
- Creating files
- Renaming files
- Moving files
- Deleting files
- Installing packages
- Running the development server
- Building the application
- Running tests
- Git operations

Benefits:

- Repeatable and documented workflow
- Reduced risk of accidental Explorer mistakes
- Easier troubleshooting
- Consistent development process
- Faster implementation

Visual Studio Code Explorer should primarily be used for:

- Editing code
- Reviewing project structure
- Debugging
- Inspecting files

---

## 2. Complete File Principle

Unless explicitly requested otherwise:

- Always implement using complete replacement files.
- Avoid partial snippets for production code.
- Keep the project compiling after every completed file.
- One implementation step should produce one working result.

---

## 3. Build Verification

Every completed implementation step must be verified before continuing.

Preferred commands:

```bash
npm run dev
```

or

```bash
npm run build
```

No new implementation begins until the current build compiles successfully.

---

## 4. Incremental Development

Development follows small, verifiable milestones.

Workflow:

Plan

↓

Terminal Commands

↓

Complete File

↓

Compile

↓

Visual Verification

↓

Git Commit

↓

Push

Every milestone should leave the project in a stable, working state.

---

## 5. Git Workflow

At the completion of every milestone:

```bash
git status
git add .
git commit -m "<meaningful commit message>"
git push origin main
```

Every commit should represent a stable build.

---

## 6. Feature Development Principle

Build complete user-facing functionality instead of isolated code.

Every component should be:

- immediately connected into the application
- visually verifiable
- extendable
- production quality

Avoid creating unused components or temporary UI that will later be discarded.

---

## 7. Architecture Stability Principle

Once an architectural decision has been implemented successfully, avoid refactoring unless there is a clear technical benefit.

Priority:

1. Stability
2. Feature delivery
3. Refactoring only when justified

The objective is continuous forward progress while maintaining a clean architecture.
